# Closing the Loop (Stage 6) — Design

## Origin

`docs/roadmap.md` Stage 6: "`PermissionRequest` approvals replacing the simulation, editable scope via `updatedInput`, `PostToolUse` block-with-reason." (~8 tasks). Expanded from `docs/competitive-gap-analysis-2026-07.md` §5/§6, item 3 (Tier 1, effort M): "Your approval queue, risk policy, TopBar bell, and AUTO-mode are the largest remaining fictional subsystem... Aether OS stops being a passive observer and becomes an **approval console**." Cites Antigravity's editable-permission-target affordance as the best approval UX seen anywhere.

## What this replaces

The current approval system is entirely fictional (`src/state/types.ts`): an `Approval { id, agent, action, detail, risk: 'HIGH'|'MED'|'LOW', verb?: 'spawn'|'kill'|'throttle' }` object generated by `tick.ts`'s random simulation and the chat action-JSON pipeline's risky-verb path. Approve/reject in `reducer.ts` is cosmetic — it filters the item out of `state.approvals`; nothing downstream is actually allowed, denied, or blocked, because there is no real process on the other end. This stage makes the queue real.

## Verified real infrastructure this design depends on

Confirmed against Claude Code's actual hooks documentation (not inferred):

**`PermissionRequest` hook** — fires before a risky tool call executes. Stdin carries `session_id`, `permission_mode`, `tool_name`, `tool_input`, `tool_use_id`. Synchronous: Claude Code spawns the hook as a child process and blocks waiting for it to exit (default up to 600s, configurable via `timeout`/`async` in the hook's `settings.json` entry) before proceeding. Exit 0 + valid JSON on stdout applies the decision:
```json
{ "hookSpecificOutput": { "hookEventName": "PermissionRequest",
  "decision": { "behavior": "allow" | "deny", "updatedInput": { ... } } } }
```
Exit 2 denies using stderr as the shown reason. **`updatedInput` genuinely lets a hook rewrite the tool's parameters before execution** — this is the real basis for "editable scope."

**`PostToolUse` hook** — fires after a tool call has already executed; it cannot prevent or undo the action. Stdin adds `tool_output`. A `"decision": "block"` in the stdout JSON stops Claude from treating that turn as done and forces it to address the reason on its next turn — it does not roll back anything. Exit 2 is non-blocking (tool already ran; stderr just logged).

Both are configured the same way as existing hooks — a `command` entry under `hooks.PermissionRequest` / `hooks.PostToolUse` in `.claude/settings.json`, matched by tool-name pattern.

## Scope decisions (resolved during brainstorming)

- **Session scope: Aether's own tracked session only**, not fleet-wide. The hook script checks the incoming `session_id` against Stage 4's existing `own-session.json` pinned-session file — reused infra, not new scoping logic. A mismatch (a different session, e.g. from the fleet) falls through non-blocking, same as "app not running."
- **App-not-running fallback: fall through to Claude Code's native prompt/hooks**, not default-deny. The hook script attempts a short-timeout (~500ms) connection to the local server; failure means "app isn't open," and it exits non-blocking rather than stalling or denying.
- **IPC mechanism: a local HTTP server in Electron's main process**, listening on localhost, port discoverable via a file under `~/.aether-os/` (matching the existing port-file/statusline-payload discovery convention). The hook script POSTs the request and the connection stays open until the renderer responds or a safety timeout elapses — well under Claude's own 600s cap (target: 120s for `PermissionRequest`).
- **Risk tiering: a new tool-based policy**, replacing the old verb-based table (kill/spawn/throttle don't exist as real tool names). Maps real `tool_name` + `tool_input` patterns to LOW/MED/HIGH (e.g. Bash with `rm`/`sudo`/pipe-to-shell → HIGH; Write/Edit → MED; Read/Grep/Glob → LOW). **Styling and urgency only — no auto-approve.** Every `PermissionRequest` always shows the user a prompt in this stage; auto-approve policy is real unattended automation and is explicitly deferred to a later stage.
- **Scope editor: a single per-tool-aware editable field**, not a raw JSON editor. Pre-filled with the most relevant parameter — file path for Read/Write/Edit (editable inline, e.g. widened to a glob), command string for Bash.
- **`PostToolUse` trigger: automatic detection, manual review only on trip.** This was the key design resolution: rather than holding every single tool call open for a possible manual flag (which would add latency to 100% of tool calls for a feature only occasionally used), the `PostToolUse` hook's server-side handler runs Stage 5's existing, already-tested anomaly detectors (`detectReReadLoop`, `detectWriteDeleteRewrite`, `detectZeroEditBurn` from `src/shared/anomalyDetectors.ts`) against Electron's **live, per-second** in-memory tool-call history (the same history `liveAgentTracker.ts` already maintains from the pty stream — not the headless collector's ~15s-poll copy, which would be too stale for a synchronous hook decision). A clean pass (the overwhelming majority of calls) returns an immediate allow with zero added latency and no UI shown. A tripped detector holds the request open (same pattern/timeout as `PermissionRequest`) and shows a flag card; the user decides to block (with a reason, delivered via `decision: "block"`) or dismiss (allow through).

## Architecture

```
Claude Code
  │ PermissionRequest / PostToolUse (stdin JSON)
  ▼
hook script (new, PowerShell)
  │ session_id check against own-session.json (Stage 4 infra)
  │   mismatch/app-unreachable → exit non-blocking, fall through
  ▼
electron/permissionServer.ts (new, local HTTP server, main process)
  │ PermissionRequest: always resolves via renderer UI
  │ PostToolUse: runs Stage 5 detectors against live history first;
  │   clean → instant allow; tripped → resolves via renderer UI
  ▼
renderer (new PermissionRequestCard / flag card)
  │ user decision (approve/deny/edit scope, or block/dismiss)
  ▼
back through the still-open HTTP response → hook script → Claude Code
```

| File | Purpose |
|---|---|
| `electron/permissionServer.ts` (new) | Local HTTP server; `POST /permission-request`, `POST /post-tool-flag-check`; per-`tool_use_id` pending-Promise resolution; timeout-based auto-deny/auto-allow. |
| Hook script (new, Node `.mjs`) | **Correction post-approval:** the existing hook precedent (`scripts/aether-hook-emit.mjs`, invoked via `node "${scriptPath}"`) is Node, not PowerShell — no `.ps1` script exists anywhere in this repo, and nothing about the hook contract requires PowerShell. The new script follows that precedent. Reads stdin, checks session, POSTs with short connect-timeout, translates the HTTP response into Claude Code's exact expected JSON/exit-code contract. |
| `collector/src/hookInstaller.ts` (extend Stage 2) | **Correction post-approval:** lives under `collector/src/`, not `electron/`. `MANAGED_HOOK_EVENTS` already includes `PostToolUse` (currently used for the collector's own spool ingestion) — Stage 6's PostToolUse hook is a **second group appended to that existing array** (the installer already supports multiple marker-keyed groups per event), not a replacement. `PermissionRequest` is not yet managed and must be added to the list. |
| `src/shared/permissionRisk.ts` (new, pure) | `tool_name` + `tool_input` → `'LOW' \| 'MED' \| 'HIGH'`. |
| `src/state/types.ts` | New `PermissionRequestUI` shape (requestId, toolName, toolInput, editable field, risk, sessionId) — separate from the old fictional `Approval`. **Correction post-approval:** `Approval`/`ADD_APPROVAL`/`state.approvals` are referenced across 17 files (persistence, chat action-JSON pipeline, `TopBar`'s bell, terminal commands, multiple test files) — not just the two call sites originally assumed. The keep-vs-remove decision needs its own properly-scoped task, not a quick check. |
| Renderer: `PermissionRequestCard` / flag card (new) | Per-tool-aware editable field, risk badge, Approve/Deny (or Block/Dismiss) actions, IPC round-trip to main to resolve the held HTTP response. |

## Error handling

- Server unreachable or session mismatch → hook falls through non-blocking; no crash path, no orphaned Claude Code process.
- Renderer never responds within timeout → auto-deny (`PermissionRequest`) / auto-allow (`PostToolUse` flag), each with a stated timeout reason — a stuck UI cannot hang Claude Code indefinitely.
- Malformed/unexpected hook JSON → hook script logs and fails safe (non-blocking exit); never partially blocks.

## Testing

- `permissionRisk.ts` — pure unit tests, tool/input → tier table.
- `permissionServer.ts` — integration tests against a real local HTTP server (this codebase's established "real round trip, not mocks" convention), including the timeout auto-deny/auto-allow paths.
- Hook script — PowerShell invoked by Claude Code; test via a thin wrapper if feasible, otherwise documented as needing manual verification (this dev environment is headless — same disclosed limitation as Stage 4/5).
- Session-mismatch and app-not-running fallback paths get explicit tests — both are silent-failure-shaped branches, and this project's convention is to never let "looks handled" mask a silent gap.

## Explicitly deferred (not this stage)

- Fleet-wide approval control (any session, not just Aether's own) — a much larger scope/security surface, left for a future stage if ever pursued.
- Auto-approve by risk tier — real unattended automation; the risk policy this stage builds is styling-only until a later stage decides to act on it.
- A generic raw-JSON scope editor — the per-tool-aware single-field editor covers the primary use case (Antigravity-style scope widening) without the rougher raw-JSON UX.
