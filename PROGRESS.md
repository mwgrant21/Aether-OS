  **(b) The blend ratio is an assumption, and it is the estimate's entire error term.** `CompletedDispatchUsage.tokens` comes from `<subagent_tokens>` in a task-notification: one scalar with no input/output/cache split, so a per-dispatch dollar figure requires assuming a mix. Claude Code does not document what that scalar counts and this repo had no statement of it either, so the ratio was **inferred from magnitude and the inference written into the source rather than buried**: an observed dispatch reported ~83k tokens across 24 tool uses, and if that were a total *including cache reads* it would imply ~3.5k tokens per turn for an agent whose system prompt alone exceeds that — implausible, since a real total-with-cache figure for that much tool work runs to millions. The scalar therefore behaves like generated tokens, not context tokens. `DISPATCH_OUTPUT_SHARE = 0.8` keeps a fifth priced as input rather than asserting a purity the evidence does not quite support. **Error direction, stated plainly:** a dispatch more output-heavy than this is *under*-estimated and a more input-heavy one *over*-estimated; if the scalar turns out to be output tokens exactly, every estimate here is ~16% low at every tier and the correct fix is raising that one constant to `1.0`, not adjusting anything downstream. A test pins the value so it cannot move silently.

  **(c) The residual is rendered, never normalized.** `reconcile()` returns a *signed* figure that is neither clamped nor absolute, and the view displays it: "dispatch estimates account for ~$X of the $Y session total; ~$Z unattributed." A **negative** residual is a real and meaningful outcome — it means the estimator is over-claiming, which is exactly the evidence that the blend ratio in (b) needs revisiting — so it renders as "over-attributed" rather than being hidden. A ledger that balances by concealing its error is lying.

  **(d) Periods without collector data render as gaps, not zeroes.** Every rollup bucket is `number | null` at the type level, so no renderer can accidentally default a missing period to `0`; `null` renders "no data — collector not running" and never `$0.00`. Tested from both directions — a null bucket produces the gap and no `$0.00` anywhere, and an observed-but-genuinely-free period produces `$0.00` and no gap. Sub-cent totals floor to `<$0.01` for the same reason: rounding a real cost to `$0.00` reads as free.

  **(e) Limitation 5 — this view cannot see spend that did not pass through a transcript.** A raw API key billed by something else entirely is invisible here, and that is the exact shape of *both* incidents that motivated this stage. The view's own header copy therefore scopes its claim to "observed in this machine's Claude Code transcripts" rather than implying it is the account's bill. **The Ledger narrows the search; it does not close it.** Do not let this entry, or the view, be read as saying otherwise.
